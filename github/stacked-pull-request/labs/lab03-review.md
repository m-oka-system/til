# Lab 03: Web UI でレビューする

所要 30 分 | 舞台: github.com（CLI は補助）

---

## ゴール

レビュアー側の体験を理解する。「なぜスタックだとレビューが速いのか」を、
実際の画面で確認する。

## 開始状態

[Lab 01](lab01-first-stack.md) 完了。3 本の PR が GitHub 上にある。

```bash
cd "${PLAYGROUND_DIR:-$HOME/stacked-pr-playground}" && gh pr list
```

---

## Step 1: 層ごとの差分を確認する

最下層の PR をブラウザで開きます。

```bash
gh stack bottom
gh pr view --web
```

**"Files changed" タブ**を見てください。

| PR                      | 表示されるファイル  |
| ----------------------- | ------------------- |
| PR #1 `feat/task-model` | `src/model.js` のみ |
| PR #2 `feat/task-store` | `src/store.js` のみ |
| PR #3 `feat/task-api`   | `src/api.js` のみ   |

3 つ順に開いて確認します。

```bash
gh stack up && gh pr view --web
gh stack up && gh pr view --web
```

### なぜこうなるか

PR #2 の base は `feat/task-model` です。差分は
「`feat/task-store` と `feat/task-model` の差」なので、`src/model.js` は含まれません。

**この表示自体は従来のブランチ運用でも、base を手で設定すれば同じように得られました。**
スタックが引き受けるのは、その base を積むたびに設定し、下層が動いても維持し続ける部分です
（詳しくは Lab 04・Lab 07）。

## Step 2: stack map を読む

**stack map** は Conversation タブ下部の **merge box の中**にあります。
スタック内の全 PR と、今どこを見ているかが示されます。

**確認すること:**

- 今開いている層にマーカーが付いている
- 各層の PR タイトル、レビュー状態、CI の状態が並んでいる
- クリックで他の層に移動できる

> [!NOTE]
>
> **ヘッダーの stack icon と混同しやすいので注意します。**
> PR タイトル下の `Open` バッジの隣に、`3/3` のような数字つきのスタックアイコンがあります。
> これは「スタック内の何層目を見ているか」の表示で、クリックすると
> スタック全体を並べたポップオーバー（`Stack #4` など）が開きます。
>
> |                | 場所                          | できること                                       |
> | -------------- | ----------------------------- | ------------------------------------------------ |
> | **stack icon** | ヘッダー（`Open` バッジの隣） | 現在の層番号の表示、層の移動、**`Add to stack`** |
> | **stack map**  | merge box の中                | 全層のレビュー状態・CI 状態の俯瞰、層の移動      |
>
> どちらもスタック全体を出して移動できるので紛らわしいのですが、
> **`Add to stack` があるのはヘッダー側だけ**です。ここで見分けられます。
> 公式ドキュメントが "stack map" と呼んでいるのは merge box 側です。

レビュアーはこれを見て「この変更が全体のどの部分か」を把握します。
1 層だけ見ていても文脈を失わない、というのが stack map の役割です。

## Step 3: 並行レビューを体験する

スタックの利点は **3 人が同時にレビューできる**ことです。
1 人で実習しているので、擬似的に再現します。

### 3-1. 各層に別々のレビューコメントを付ける

PR #1 の `src/model.js` の `validateTask` 関数にコメントします。

```bash
gh stack bottom
# --repo を付けないとカレントディレクトリのリモートが対象になる
gh pr comment --repo "$(gh api user --jq .login)/${PLAYGROUND_REPO:-stacked-pr-playground}" \
  "$(gh pr view --json number --jq .number)" \
  --body "title の長さ上限チェックも必要では？"
```

PR #3 にもコメントします。

```bash
gh stack top
gh pr comment --repo "$(gh api user --jq .login)/${PLAYGROUND_REPO:-stacked-pr-playground}" \
  "$(gh pr view --json number --jq .number)" \
  --body "DELETE のレスポンスに body がないのは意図通り？"
```

### 3-2. 重要な観察

いま、**PR #1 のレビューが終わっていなくても PR #3 のレビューが進んでいます**。
従来の 1 本の大きな PR では、これは 1 つのスレッドに全部のコメントが混ざり、
レビュアー同士が同じファイルを見て衝突していました。

## Step 4: レビュー承認と CI 状態を確認する

```bash
gh pr status
gh stack view
```

`gh stack view` の出力に、各層のレビュー状態・チェック状態が含まれます。
「どの層で止まっているか」がこれで一目で分かります。

> [!IMPORTANT]
>
> **すべての層**に必須レビューと必須ステータスチェックが適用されます。
> `main` を直接ターゲットしていない中間層も例外ではありません。
> これは [Lab 09](lab09-ci-protection.md) で実際に検証します。

---

## Step 5: Web UI からスタックに層を足す

CLI を使わずに、ブラウザから層を追加することもできます。

1. スタック内の任意の PR を開く
2. **stack アイコン**をクリック
3. **Add to stack** を選択

新しい PR の base は自動的に**最上層のブランチ**に設定されます。

> [!NOTE]
> Web UI から追加できるのは「最上層への追加」です。
> **途中への挿入や並べ替えは CLI (`gh stack modify`) が必要**で、Web UI に相当機能はありません。
> これは [Lab 06](lab06-modify.md) で扱います。

## Step 6: レビュアーの立場で分割の良し悪しを判定する

3 つの PR を順に見て、次を自問してください。

- この層だけを見て、**何をしようとしているか**が分かるか
- この層だけで **CI が通る**か
- この層だけを `main` にマージしても**壊れない**か（機能は不完全でよいが、壊れてはいけない）
- 15 分以内に読み切れるか

4 つとも Yes なら良い分割です。
No が出る層があれば、それは切り方がずれているサインです。

### 悪い分割の例

| 分割                                       | 何が問題か                                             |
| ------------------------------------------ | ------------------------------------------------------ |
| 「ファイル A の変更」「ファイル B の変更」 | ファイル単位。レビュアーは意図を読み取れない           |
| 「実装」「テスト」                         | 実装層だけで CI が通らない。テストは実装と同じ層に置く |
| 「500 行」「500 行」                       | 行数で機械的に割った。境界に意味がない                 |

### 良い分割の軸

- **依存の方向**: 下位レイヤー → 上位レイヤー
- **性質の違い**: 純粋なリファクタリング → 振る舞いの変更
- **可逆性**: **上の層から順に**戻せる単位
  （下層だけを単独で revert しても壊れない、とは限りません。
  依存構造との関係は [10. ロールアウト設計](../docs/10-rollout.md) の「層の切り方」で扱います）

## つまずきポイント

| 症状                                 | 原因と対処                                                                                                                                                                     |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| PR #2 の差分に `model.js` が混ざる   | base が `main` になっている。手動で PR を作った可能性。`gh stack submit` で作り直す                                                                                            |
| stack map が表示されない             | PR がスタックとしてリンクされていない。`gh stack submit` または `gh stack link` を実行                                                                                         |
| 中間層の PR で必須チェックが走らない | **`branches: [main]` 制限は原因ではない**（スタックでは全層で発火する。[Lab 09](lab09-ci-protection.md) 参照）。`paths` フィルタや `if` 条件、必須チェックの登録漏れを確認する |

## 振り返り課題

1. スタックにすることでレビュー時間が短縮される理由を、
   「差分の大きさ」以外の観点で 1 つ挙げよ。
2. 「実装 PR」と「テスト PR」に分けてはいけない理由は。
3. レビュアーとして PR #2 だけを見ているとき、
   PR #1 の設計判断が気に入らなかった。どこにコメントすべきか。

<details>
<summary>解答</summary>

1. 並行レビューができるため、レビューが 1 人にシリアライズされない。
   また下層が承認され次第マージできるので、待ち時間中も作業が進む。
   （他: 層ごとに適切なレビュアーを割り当てられる、CODEOWNERS が層単位で効く など）
2. 実装層だけでは CI が通らず、各層が独立して健全であるという原則を破る。
   また「テストのない状態でマージされうる」危険がある。テストは対応する実装と同じ層に置く。
3. PR #1 側にコメントする。PR #2 のスレッドに書いても、PR #1 の作者・レビュアーの目に留まらず、
   修正しても PR #2 の差分には現れない。stack map から PR #1 に飛んでコメントするのが正しい。

</details>
