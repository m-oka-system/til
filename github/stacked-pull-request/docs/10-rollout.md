# 10. 組織へのロールアウト設計

座学 + 設計演習 | 対象: テックリード / プラットフォームチーム

---

## 前提

Lab 01〜09 を終えて、機能の挙動と限界が体感として分かっている状態を想定します。
ここからは「自分のチーム・組織に入れるか、入れるならどう入れるか」を設計します。

---

## 1. 導入判断: そもそも入れるべきか

### 効果が大きいチーム

| 条件                                       | 理由                          |
| ------------------------------------------ | ----------------------------- |
| PR が日常的に 500 行を超える               | 分割の効果が直接効く          |
| レビュー待ちがボトルネックになっている     | 並行レビューで待ち時間が減る  |
| 複数チームのオーナーがまたがる変更が多い   | CODEOWNERS が層ごとに分かれる |
| 大規模移行・リファクタリングが継続的にある | 段階的に着地させられる        |

### 効果が小さい / 逆効果なチーム

| 条件                                   | 理由                            |
| -------------------------------------- | ------------------------------- |
| PR が元々 100 行程度                   | 分割コストが利益を上回る        |
| CI が遅い（15 分以上）かつ実行枠が逼迫 | CI 実行回数が層数倍になり詰まる |
| fork ベースの OSS コントリビュートが主 | cross-fork 非対応で使えない     |
| CLI を使わないメンバーが大半           | 並べ替えができず運用が硬直する  |

> [!IMPORTANT]
>
> **CI コストは最大の導入障壁です。** [Lab 09](../labs/lab09-ci-protection.md) の見積もりを
> 自チームの数字で必ず計算してから判断してください。

## 2. パイロット設計

いきなり全社展開しないこと。公式ドキュメントも小規模パイロットを推奨しています。

### パイロットの設計テンプレート

| 項目           | 決めること                                 | 記入例                           |
| -------------- | ------------------------------------------ | -------------------------------- |
| 対象チーム     | 1 チーム、3〜6 人                          | プラットフォームチーム           |
| 対象リポジトリ | 既存のブランチ保護と CI がそのまま効くもの | `internal-api`                   |
| 期間           | 2〜4 週間                                  | 3 週間                           |
| 対象作業       | 分割しやすい大きめの変更を 2〜3 件         | 認証基盤の刷新                   |
| 成功指標       | 下記参照                                   | —                                |
| 中止条件       | 事前に決めておく                           | CI 待ち時間が 2 倍を超えたら中止 |

### 測る指標

| 指標                   | 測り方                           | 期待する変化                   |
| ---------------------- | -------------------------------- | ------------------------------ |
| PR あたりの変更行数    | PR の追加 + 削除行数の中央値     | 減る                           |
| 初回レビューまでの時間 | PR 作成 → 最初のレビューコメント | 短くなる                       |
| PR のライフタイム      | 作成 → マージ                    | 短くなる                       |
| CI 実行時間の合計      | Actions の使用量                 | **増える**（許容範囲かを見る） |
| レビュアーあたりの負荷 | 1 人が読む行数                   | 減る                           |

> [!TIP]
>
> **「CI 時間が増える」ことは失敗ではありません。** 増加分が
> レビュー時間の短縮に見合うかを判断するための数字です。
> 最初から「増える」前提で見積もっておくと、議論が感情論になりません。

## 3. チーム規約として決めること

### 3-1. 層の切り方

**規約案:**

- 1 層 = 1 つの論理的な変更。ファイル単位・行数単位で切らない
- 各層は**単体で CI を通る**こと
- 層数は **3〜5** を目安とする（それ以上は分割の切り口を見直す）
- テストは対応する実装と**同じ層**に置く

> [!WARNING]
>
> **「各層は単体で revert しても壊れない」は規約にできません。**
> スタックは層が下に依存する構造なので、上層がマージされたあとに下層だけを revert すると、
> 依存先が消えて `main` が壊れます。本教材の題材でいえば、`store` と `api` がマージ済みの状態で
> `model` 層だけを revert する場合がこれに当たります。
> squash マージは revert の**単位**を作るだけで、安全性までは保証しません。
>
> 巻き戻しが必要になったら **上の層から逆順に revert する**のが原則です。
> どうしても下層だけを戻したい場合は、互換レイヤーを残すか、機能フラグで無効化できる設計にしておきます。

### 3-2. 層の順序

- **依存される側を下に**置く（下位レイヤー → 上位レイヤー）
- **独立した変更は最下層**に置く（先に着地できる）
- **全層が触る共有ファイル**（バレルファイル、設定、ロックファイル）は
  可能なら**最上層**にまとめる（コンフリクトの伝播を最小化）

> [!IMPORTANT]
> 並べ替えには `gh stack` 拡張が必須です（Web UI に相当機能なし）。
> **CLI を使わないチームは、順序を最初に慎重に決める必要があります。**
> あるいは全員に拡張を入れてもらう。この二択を明示的に選んでください。

### 3-3. マージ方式

- **squash 推奨**: 1 層 = `main` 上の 1 コミット。層単位で revert できる
- リポジトリ設定で squash が無効なら、merge commit で運用しつつ
  「層内のコミットも読める粒度に保つ」ことを規約にする

### 3-4. 日常オペレーション

| タイミング       | やること                                             |
| ---------------- | ---------------------------------------------------- |
| 作業開始時       | `gh stack sync` で最新化                             |
| 下層を修正したら | `gh stack sync`（rebase + push + PR 同期）           |
| マージ後         | `gh stack sync --prune`                              |
| 詰まったら       | `gh stack rebase --abort` で引き返す。無理に進めない |

> [!IMPORTANT]
>
> **導入前に `dismiss_stale_reviews`（新しい push で既存の承認を破棄する設定）を確認してください。**
> この設定が有効なリポジトリでは、スタックの利点が大きく削がれます。
>
> 下層を直すたびに `gh stack sync` が上層をリベースして再 push するため、
> **並行して得た上層の承認がそのつど失効し、再承認の連鎖が起きます。**
> 「承認をもらったら待たずに次の層へ進む」という前提が成立しなくなります。
>
> 現在値は次で確認できます（リポジトリの管理者権限が必要です）。
>
> ```bash
> gh api "repos/<owner>/<repo>/branches/main/protection" \
>   --jq '.required_pull_request_reviews.dismiss_stale_reviews'
> ```
>
> ブランチ保護が未設定なら `404` が返ります。その場合この問題は起きません。
> ruleset で管理している組織では `gh api "repos/<owner>/<repo>/rulesets"` 側も確認してください。
>
> 確認したうえで、次のどちらかを選んでください。
>
> - `dismiss_stale_reviews` を**無効にする** — レビューの厳格さとのトレードオフを受け入れる
> - **有効のまま運用する** — 下層が固まるまで上層のレビューを依頼しない。
>   並行レビューの利点は諦め、「PR が小さく読みやすい」という利点だけを取る
>
> この確認を飛ばすと、導入の主目的である並行レビューが機能しません。

**禁止事項:**

- スタックのブランチへの生の `git push --force`
- `gh stack rebase` の途中で `git rebase --continue` を使うこと

### 3-5. スタックのライフサイクル

- 全 PR がマージされると**スタックは閉じる**
- 閉じたスタックには後から層を足せない
- 関連作業が続く場合は、**全部マージしきる前に層を積む**か、新しいスタックを作る

## 4. CI の設計

### 4-1. ジョブの階層化

| ジョブ                            | 実行範囲                 | 理由                                         |
| --------------------------------- | ------------------------ | -------------------------------------------- |
| Lint / 型チェック / 単体テスト    | **全層**                 | 各層の健全性の保証。部分マージの前提が崩れる |
| 統合テスト                        | 全層（コストが許すなら） | 下層が壊れれば上層も壊れる                   |
| E2E / 性能 / セキュリティスキャン | **最上層のみ**           | ここでコストを削る                           |
| デプロイプレビュー                | 最上層のみ               | 層ごとに環境を立てる意味が薄い               |

### 4-2. スタックメタデータの活用

- ワークフローからは `github.event.pull_request.stack` で参照できる
- 通常の PR では `null`。既存のワークフローは**そのまま動く**（後方互換）
- **フィールド構成は preview 中に変わる可能性がある**。
  ハードコードする前に、実際の出力をログで確認すること（[Lab 09 Step 3](../labs/lab09-ci-protection.md)）

### 4-3. 実行枠の保護

```yaml
concurrency:
  # pull_request 以外のイベント（push など）では github.event.pull_request が null になり、
  # グループ名が "ci-" に潰れて無関係な実行どうしが相互キャンセルする。
  # 既存のワークフローへ入れる場合はフォールバックを必ず置くこと。
  group: ci-${{ github.event.pull_request.number || github.ref }}
  cancel-in-progress: true
```

`sync` のたびに全層がリベースされ再実行がかかるため、
古い実行のキャンセルは実質必須です。

## 5. ブランチ保護の設計

公式ドキュメントの前提:

- 必須レビュー・必須ステータスチェックは、**スタックの base ブランチに対して**全 PR で評価される
- **CODEOWNERS はすべての層に適用される**
- マージは、対象 PR と**その下の全依存層**が要件を満たすまでブロックされる

**設計上の含意:**

| 論点              | 検討事項                                                                   |
| ----------------- | -------------------------------------------------------------------------- |
| 必須チェックの数  | 層数倍になるので、必須にするチェックは絞る                                 |
| 必須レビュー数    | 2 人必須にすると、5 層で 10 承認が必要。1 人に緩める判断も検討             |
| CODEOWNERS の粒度 | 層の切り方と CODEOWNERS の境界を**揃える**と効果が最大化する               |
| merge queue       | **完全対応**。ただしキュー使用時はマージ方式がキュー側の設定で上書きされる |

> [!TIP]
>
> **CODEOWNERS の境界に合わせて層を切る**のが、スタックの効果を最大化する設計です。
> 「この層は `@api-team` だけが見ればいい」という状態を作れれば、
> レビューは真に並列化します。

## 6. API / 自動化ツールの移行

既存の自動化ツール（自動マージ bot、リリースツール、ダッシュボード）への影響です。

| 項目         | 内容                                                                                        |
| ------------ | ------------------------------------------------------------------------------------------- |
| **REST API** | PR オブジェクトに `stack` メタデータが含まれる。通常 PR では `null`                         |
| **Webhook**  | ペイロードに `stack` フィールドが追加される。`stacked` アクションでスタック形成を検知できる |
| **後方互換** | `stack` が `null` なので、既存の連携は**そのまま動く**                                      |
| **要対応**   | **プログラムからマージするツール**は、スタック対応のエンドポイントへの移行が必要            |

### 移行チェックリスト

- [ ] 自動マージ bot を洗い出す
- [ ] それらが従来のマージエンドポイントを使っているかを確認
- [ ] スタック対応エンドポイントへの移行、または**スタック PR は自動マージの対象外にする**
- [ ] PR メトリクスのダッシュボードで「PR 数」が増える影響を関係者に説明する
- [ ] `stacked` webhook アクションでの通知・自動化の要否を検討

> [!WARNING]
>
> **一番危険なのは自動マージ bot** です。
> スタックを認識しないツールが上層を先にマージしようとして失敗を繰り返す、
> あるいは意図しない順序でマージする可能性があります。
> パイロット期間中は、スタック PR を自動マージの対象から外すのが安全です。

## 7. 教育とオンボーディング

### 最低限教えるべき 5 コマンド

```bash
gh stack init <branch>     # スタックを始める
gh stack add <branch>      # 層を積む
gh stack submit            # PR を作る / 更新する
gh stack sync              # 最新化する（毎朝これ）
gh stack merge             # マージする（引数なし = 対話ウィザードで層を選ぶ）
```

これだけで日常業務は回ります。`modify` / `link` / `rebase --upstack` は
必要になったときに調べれば十分です。

### レビュアー向けに教えるべきこと

- stack map の読み方
- **下層の設計に対する指摘は、下層の PR に書く**（上層に書いても届かない）
- 承認したら待たずに次の層へ進んでよい
  — **ただし `dismiss_stale_reviews` が有効なリポジトリでは、下層が修正されるたびに
  上層の承認が失効する。** 有効かどうかを先に確認すること（「3-4. 日常オペレーション」参照）

### つまずきやすい 3 点

1. **`git push --force` を使ってしまう** → 追跡情報が壊れる
2. **`git rebase --continue` を使ってしまう** → カスケードが止まる
3. **下層の指摘を上層のスレッドに書く** → 修正されない

## 8. ロールアウト計画テンプレート

```
## フェーズ 1: 検証（2 週間）
- [ ] プラットフォームチーム 1 名が本カリキュラムを完了
- [ ] 自チームの CI コスト増を試算
- [ ] 自動マージ bot への影響を調査
- [ ] 導入可否を判断

## フェーズ 2: パイロット（3〜4 週間）
- [ ] 1 チーム・1 リポジトリで実運用
- [ ] チーム規約のドラフトを作成（層の切り方・順序・マージ方式）
- [ ] CI のジョブ階層化を実装
- [ ] 指標を測定し、ふりかえり

## フェーズ 3: 展開（1〜2 か月）
- [ ] 規約を確定し、社内ドキュメントに掲載
- [ ] 全員に gh-stack 拡張のインストールを案内
- [ ] ハンズオン研修を実施
- [ ] 対象リポジトリを段階的に拡大

## 継続
- [ ] preview → GA の変更を追跡（CLI 更新、API 変更）
- [ ] 四半期ごとに指標をレビュー
```

## 9. 設計演習

自分のチームを想定して、次を埋めてください。

1. **導入判断**: 効果が大きい条件・小さい条件のうち、自チームに当てはまるのはどれか。
   結論として導入すべきか。

2. **CI コスト試算**:

   ```
   現在の PR あたり CI 時間: ___ 分
   想定する層数: ___ 層
   1 スタックあたりの修正回数（想定）: ___ 回
   → スタック導入後の CI 時間: ___ 分（___ 倍）
   → 削減策を適用した場合: ___ 分
   ```

3. **層の切り方の規約**: 自チームのコードベースで、
   直近の大きな PR を 1 つ選び、それを 3〜5 層に分解する案を書く。

4. **CODEOWNERS との整合**: その分解案で、各層のオーナーは誰になるか。
   境界は揃っているか。揃っていないなら、切り方を変えられるか。

5. **自動化への影響**: 自チームの自動マージ / リリース自動化を洗い出し、
   スタック対応が必要なものを特定する。
